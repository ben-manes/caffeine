# Design Decisions (Quick Reference)

Before reporting a bug or suggesting a "fix," check this list. These are intentional.

- **Weight=0** is a pinning feature (skipped during eviction), not a bug. Instead verify weight convergence via the telescoping sum.
- **EXPIRE_TOLERANCE (1s)** is intentional inexactness — entries may expire up to 1s earlier than the configured duration (never later). Applies to both `writeTime` reorder decisions in remap and `accessTime` updates on the read path (skipped if the last update is within tolerance, to avoid hot-entry cache-line contention). Tolerance is bypassed when the configured duration is `<= tolerance`.
- **Expiration eviction is capped per maintenance cycle** (`EXPIRATION_THRESHOLD`, 1000). `expireAfterAccessEntries`/`expireAfterWriteEntries` and the variable `TimerWheel.advance` evict at most that many, then set `PROCESSING_TO_REQUIRED` to re-arm and drain the backlog across cycles (mirrors `drainWriteBuffer`). Bounds the idle-recovery spike without blocking a thread; the cap is never hit by normal traffic. The wheel rewinds `nanos` and re-links the unprocessed bucket remainder so the next advance reprocesses it. A `schedule`/`reschedule` inside that window measures `findBucket`'s duration against the rewound (behind) clock, which is **benign**: an inflated duration can only pick a *coarser* wheel, the index still comes from the entry's own deadline so it lands in that wheel's correct bucket and cascades down normally, and the target tick can never fall behind the cursor (`deadline >= now >= rewound`). Don't "fix" the stale clock — a 4000-trial probe found no observable effect. The budget counts **only evictions**, never the cascade (rescheduling non-due nodes) — that's intentionally uncapped (cheap O(1) splice, degenerate trigger). A cascade cap must **never reuse the rewind** (it re-scans → re-cascades → starves the eviction drain / livelocks); it would need a forward-carried backlog. Don't flag it as under-expiring or remove the re-arm.
- **Transient negative weightedSize** is acceptable eventual consistency. Instead verify convergence after maintenance completes.
- **accessTime uses opaque write (not CAS)** to avoid contention storms. Instead verify that stale reads cause only benign early expiration.
- **Read-path expiry extension can briefly resurrect a just-expired entry** (`tryExpireAfterRead`'s `casVariableTime`, or `setAccessTime`) — accepted, not a bug. A reader that saw the entry live and then extends it can land the write just after the entry crossed its boundary, leaving it visible slightly later than expiry. Inherent to lock-free read-extension over lazy expiration (the CAS only checks the field is unchanged, so it can't reject an expired entry; a fresh-clock guard before the write still races a context switch — only a read-path lock, rejected, closes it). Wide window needs a slow `expireAfterRead` (callback misuse). "Never later" is best-effort here; over-stay is bounded by one duration and self-heals on maintenance. Don't add a *fresh-clock* re-check guard (distinct from the load-bearing `node.getValue() == value` value-identity check that blocks rebinding a read duration onto a replaced value — keep that one).
- **notifyEviction before user code** preserves linearizability. Instead verify catch-commit-rethrow handles exceptions after irrevocable notification.
- **Catch-commit-rethrow** in doComputeIfAbsent/remap makes phantom evictions real on exception. Instead verify the committed state is consistent. This is the most commonly misunderstood pattern — read the doc before flagging exception handling in compute paths.
- **Two weight fields** (weight + policyWeight) is intentional for the telescoping sum. Instead verify both fields converge. The convergence proof depends on task ordering — read the doc before flagging negative transient sizes. `makeDead` subtracts the finalized `getWeight()` (not policyWeight) and `UpdateTask.run` is deliberately dead-guard-free — a matched pair: a late-applied UpdateTask adds back exactly the δ that makeDead over-subtracted. Don't add an isDead guard to UpdateTask or switch makeDead to policyWeight.
- **Non-volatile keyReference in WeakValueReference** is safe (published via setRelease + storeStoreFence). Instead verify the fence is present in setValue.
- **`refreshIfNeeded` is lock-free and `discardRefresh` is over-aggressive** — both intentional. The completion-path ABA guards discard spurious reloads, and any refresh racing a *real* mutation must be killed for linearizability. Don't add `synchronized(node)` to refresh or try to narrow the discard for real mutations. The one sanctioned narrowing is `RemapHints.preserveRefresh`: query-style no-ops (async-view `putIfAbsent` on a present key, a non-matching conditional `remove`/`replace`, a same-instance `compute`) keep an in-flight refresh — and **both** `BoundedLocalCache` and `UnboundedLocalCache` must honor it (the unbounded cache used to drop the hint). The same hint also **owner-scopes the refresh completion itself**: because `refreshes` holds one future per key, a by-key discard from a completion is safe only while it still owns the registration, so each completion path (`LocalLoadingCache.refresh`, `LocalAsyncLoadingCache.tryComputeRefresh`, `refreshIfNeeded`) sets `preserveRefresh = !owned` on its **reject and absent** exits — else a stale completion steals a newer refresh's token and drops its loaded value. Honoring it therefore also gates both `remap` absent exits (`n==null`, evicted-retire) and the unbounded absent exit, not just the same-instance block. The absent steal is sync-only (`refresh(k)` on an absent key registers an `asyncLoad` without inserting the entry; async inserts an in-flight future → present → reject branch). Don't reintroduce an unconditional by-key discard on a refresh-completion exit. The jcache adapter deliberately does **not** get this narrowing — the hint doesn't cross the package boundary, so its query-style ops (a failed `putIfAbsent`, a NONE-action entry processor) do discard the refresh and reset the write time; adjudicated won't-fix, see `jcache-adapter.md`. Read the doc.
- **Async sync-view mutations are physical while queries are logical** — `AsyncCache.synchronous().asMap()` treats in-flight entries as absent for queries but `KeySet.remove`/`removeAll`/`removeIf`/`retainAll` and iterator removal operate on the raw delegate. `size()`/`isEmpty()` are also physical (they delegate straight to the backing map, counting in-flight entries). Blocking everywhere invites deadlock; the split is the inherent sync-over-async tradeoff. **Value-conditional CAS ops** (`remove(k,v)`, `replace(k,v)`, `replace(k,old,new)`) are the exception to "raw" — they **block on an in-flight future** (resolve it *outside* the `compute`, then CAS inside), mirroring CHM where a mutation must take the bin lock an in-flight `compute` holds: in-flight is absent to *reads* but blocks *mutations* as if present. The `compute`/`merge` family blocks too; only the key-based removals above are raw. Bulk collection-view ops split the same way, and it's CHM-faithful: `values().removeAll`/`remove`/`retainAll` are value-searches that skip in-flight (`getIfReady` filter, like CHM `ValuesView.remove`) so they never block; `entrySet().removeAll`'s iterate-argument branch routes through the blocking `remove(k,v)` (like CHM `EntrySetView.remove` → `map.remove(k,v)` → bin lock) so it can. Don't "fix" that asymmetry — a test on the blocking path must coordinate threads (complete the future off-thread), as the `_async` conditional `remove`/`replace` tests do. The synchronous-view **read** is likewise non-linearizable: a two-step map-read-then-`getIfReady` unwrap can return the value of an in-flight future that was superseded (`put`/`invalidate`) and then completed — a value that was the mapping at no instant. Only the raw `AsyncCache.asMap()` future view is linearizable; the sync view "reads the future it found." Don't add a double-collect re-check (a map re-read on every hit for a by-design corner). This extends to the **compute path**: `synchronous().get(k, func)`/`getAll` adopt the found in-flight future's outcome (null/exception/raw-cancel/stuck) — load-coalescing (Guava-family), *not* recompute-with-caller's-function like sync `Cache.get`=`computeIfAbsent` (CHM-family) or the same view's `asMap().computeIfAbsent`. By-design, not a bug: the interface promises neither model and the sync view can't emulate async linearizability (F-E4-1 adjudicated). Don't route `get(k,func)` through `computeIfAbsent`'s retry loop.
- **`EntrySet.removeIf` hands the predicate an immutable snapshot** (`Map.entry(k,v)`), so `setValue` throws — matching ConcurrentHashMap and Guava (JDK-8078726: their inherited default `removeIf` removed *wrong* entries under concurrent updates, so they overrode it with a snapshot + conditional `replaceNode(k,null,v)`). The write-through entry is intentionally **only** for `iterator`/`spliterator`/`toArray`; the iterator-vs-`removeIf` asymmetry is deliberate, not a bug. All four views follow this (bounded, unbounded, async sync-view `AsMapView`, async raw view `AsyncEntrySet`), removing conditionally via `remove(k,v)`; the two async views delegate to the inner cache's `removeIf` (mirroring their `values().removeIf`), the raw view having previously inherited the *positional* `iterator.remove` default. Don't "restore" a write-through entry here or flag the asymmetry.
- **`TimerWheel.advance` delta=0 on sub-tick advances** is correct (e.g., `nanos = 0 → 1`; since "Fix the timer wheel wrap bias at Long.MIN_VALUE", the `-1 → 0` crossing lands on a rebased tick boundary and yields delta=1, also correct). Entries in the "last bucket" are visited on the next full wheel cycle; read-path `hasExpired` evicts on access sooner.
- **`TimerWheel.expire` detaches a bucket onto the `pending` sentinel.** Detaching is deliberate (a rescheduled node could otherwise land back in the bucket being drained and be reprocessed), but it must not leave the chain reachable only from the stack frame — a nested `deschedule` arrives with a node reference already in hand and would strand the remainder. Keep all three properties: the head lives in a **field** (`pending.next`) and the loop re-reads it each iteration instead of carrying `next` across the `evictEntry` callback; both lists stay **circular** (a linear/sentinel-less chain breaks `reschedule`'s `getNextInVariableOrder() != null` scheduled-check — the invariant is *scheduled ⟺ non-null links*); and `advance` **defers while the `advancing` flag is set** so a recursive advance can't append to the list being processed or move `nanos` beneath the caller. Don't infer that predicate from `pending` being non-empty — the outer walk empties it when it unlinks its last node, which lets a nested advance through (a real defect in the first cut, caught by the fuzzer). A self-closing ring fixes the live-bucket splice but not the stranding. Pinned by `BoundedLocalCacheTest.maintenance_recursive` and the re-entrant `TimerWheelFuzzer`. Read the doc.
- **A contract-violating user component is the user's problem** — a throwing `Ticker`/`Weigher`/`Expiry`/loader, a broken `equals`/`hashCode`, a hostile `CompletableFuture`, `Error`/OOME. The guarded/unguarded split is deliberate: fire-and-forget extensions (`StatsCounter`, `Scheduler`, removal/eviction listeners) are wrapped because a default exists; **value-bearing** ones must propagate because there is no default to recover from — `Ticker` is on the correct side of that line, not an asymmetry. The recurring finding shape is a value-bearing throw landing *after* a commit (`AddTask`/`UpdateTask` advance the weight counters before `expirationTicker().read()`; completion prologues read `statsTicker()` before their cleanup) — the mechanisms are **real and present**, so confirm-and-close rather than proposing containment; the containment op is usually throw-prone on the same trigger. No javadoc must-not-throw clause either (considered, declined). Separately, **a throw inside `maintenance` defers work, it doesn't lose it** — the `finally` lands on `IDLE`, the tasks stay in the write buffer, the next write re-arms, and a full buffer forces the inline fallback; don't force `REQUIRED` on the exception path. Read the doc.
- **`TimerWheel.getExpirationDelay` returns when a bucket is next *flushed*, not when an entry is due** — a flush expires the entry *or* **cascades it to a finer wheel**, so the wake-up matters even when nothing is due then. `expire` covers ticks `[previousTicks, previousTicks + delta]`, so a bucket at offset *b* flushes at `(b << SHIFT[i]) - (nanos & spanMask)`, and the **current** bucket — its tick already passed — flushes at offset **1**, not a full `SPANS[i]`. Both computing sites must honor that: the main scan clamps with `Math.max(1, j - start)` (don't restore the `delay > 0 ? delay : SPANS[i]` ternary — it's dead once `buckets >= 1`), and `peekAhead` probes the higher wheel's **current** bucket as well as `ticks + 1`. Returning a full span from an occupied current bucket also short-circuited before `start + 1`, so a far-future entry masked an imminent one and it fired up to a span late (68.7s / 1.22h / 1.63d; wheel 0 is absorbed by `Pacer.TOLERANCE`). It gets occupied because `findBucket` picks the **wheel by duration** but the **index by absolute time**, so a duration within `nanos & spanMask` of `SPANS[i+1]` wraps a whole revolution onto it. The `peekAhead` leg is benign alone (only wrap-arounds land there — measured), fixed so that derivation isn't load-bearing. Partial-drain remainders are unaffected (`expireVariableEntries` re-arms via `PROCESSING_TO_REQUIRED`). Pinned by `getExpirationDelay_occupiedCurrentBucket` + `getExpirationDelay_fuzzy`, which now asserts exact equality against an all-bucket oracle (its old assertion was vacuous — self-guarded, and absolute vs relative time). Read the doc.
- **`Pacer.calculateSchedule` bumps a would-be 0L result to 1L** — `nextFireTime = 0L` is the unscheduled sentinel. Don't remove the guard.
- **`LoadingCache.getAll` is not atomic; a null value is handled differently per path** — the Javadoc's "the mapping is left unestablished" is singular, so valid entries are partial-committed rather than rolled back. A *per-key* loader returning null drops just that key and keeps the rest. A *bulk* loader's returned map must not contain a null *value*: it is rejected (the whole load fails, matching Guava and the sync bulk path), not silently dropped. Omit a key to signal "no value" — an omitted requested key is dropped; only an explicit null value is rejected. (The async bulk path once dropped null values; that was reverted so all bulk paths reject.)
- **`Caffeine.from(CaffeineSpec)` disables strict parsing** — mirrors Guava's `CacheBuilderSpec`; permits programmatic overrides like adding a weigher after `maximumSize`. The footgun of disabled eviction is accepted.
- **Climber `adjustment` is a multi-cycle carry-over**, not stale state. A window transfer capped at `QUEUE_TRANSFER_THRESHOLD` (e.g. 1000 nodes/cycle) stores the unfulfilled remainder back via `setAdjustment`, and `determineAdjustment`'s sub-sample early-return (`requestCount < effectiveSampleSize`) preserves it so `climb` keeps draining the transfer across cycles until the sample refills and overwrites it. The symmetric give-back keeps the partition sum constant; a leftover smaller than every candidate's weight pins the window until a real sample lands. Don't flag "adjustment re-applied without a fresh sample." **The `quota` itself is a soft knob for a probabilistic guess, not an accounting invariant** — a transient negative `policyWeight` inflates it (`quota < weight` false, `quota -= weight` grows it), so the give-back can move `windowMaximum`/`mainProtectedMaximum` the wrong way or out of `[0, maximum]`. Not a defect, don't clamp it: the partition sum holds, the region weighted sizes stay exact, an out-of-range maximum only drains that region for a cycle and re-clamps on the next call. What must hold is that `policyWeight` converges so a region's size reflects its entries; where a mid-flight snapshot lands on the quota is meaningless (adjudicated 2026-07-27 after four re-derivations). Read the doc.
- **Async load completions are quiet updates** — `handleCompletion`/`fillProxies` call `replace(..., quietly= true)`, so the UpdateTask finalizes weight/expiry but skips the sketch increment and the climber's hit counter (a completion is bookkeeping, not a usage; loud completions measurably skewed admission and the climber's sample). A same-weight, within-tolerance quiet update skips policy work entirely (position/write time are at most tolerance-stale), and a same-instance completion preserves an in-flight refresh (`shouldDiscardRefresh= false` — a finalization is not a mutation). Don't re-add access recording there or flag the loud-user-write vs quiet-completion asymmetry. `BoundedVarExpiration.setExpiresAfter` is quiet for the same reason: it posts its reschedule through `afterWrite` (the lossy `afterRead` dropped it), and the jcache adapter calls it on **every** read for a non-eternal `ExpiryPolicy`, so a loud task would count each hit twice.
- **`BoundedLocalCache.equals` uses size + iterate-this + count==expectedSize**, not CHM-style two-sided iteration. AbstractMap-style is symmetric with the most common comparison target (HashMap), `BLC.size()` is reliable enough that the prescreen earns its keep, and O(n) beats O(n+m). The `count == expectedSize` postcondition catches the f6071dd race shape: maintenance trimming dead entries between the size prescreen and iteration would otherwise yield a silent false-true on the surviving subset. Don't propose CHM's no-size two-sided iteration here. The same pattern is mirrored in `LocalAsyncCache.AsMapView.equals` (the future-typed view).
